## 一句话结论

1. **两家中转都是真的智谱 glm-5.3-flash。** 决定性证据是跨账号缓存：
   - 官方 key 写入的文档，两家中转各读 4 次，4 次都命中；两家中转写入的文档，官方各读 4 次，也都命中。
   - 对照组用全新文档，4 次都是 0。
   - 智谱的隐式缓存全局共享，只有同一后端才会互相命中。
   - 分词增量与官方逐位相同，知识、智力、图片识别也都和官方一致。
2. **没有发现注入。** 最短的请求三家都计 17 token；加一句 system 三家都多 7 token；四类文本的分词增量完全相同。原样回显和 system 指令都正常。"有没有隐藏指令"这类问答，三家的回答分布和官方一样，官方自己也会复述一句默认提示词。
3. **junliai 的问题都出在中转层，模型本身没问题：**
   - **计费配反了。** 缓存命中按 2.8、输出按 0.23 收费，而官方是命中 0.23、输出 2.8。缓存命中比新输入还贵 3.5 倍。Claude Code、Agent 这类以缓存为主的用法，同样的活比 ikuncode 贵约 5 倍（按各自站内 $ 计，见 §11）。
   - **参数被改写，而且测试中途换过线路。**
     - 23:05–01:22（测试主体）走 Responses 转换线路：`max_tokens`、`stop`、JSON 模式、关思考都被丢掉，`reasoning_effort=low` 被当成 high。
     - 约 01:30 以后，非流式请求改走官方原样线路，`max_tokens` 开始生效，但 `reasoning_effort` 仍然被丢掉，JSON 模式仍然无效。
     - 流式请求多数仍走 `resp_` 线路。两条线路在混用，你拿到哪条自己控制不了。
   - **Anthropic 接口 `/v1/messages`（Claude Code 走这个）默认几乎不思考。** 写代码题只思考 36–38 个字符，官方是 7.6k–14k 字符。传 `thinking.enabled` 没用，只有 `output_config.effort: "max"` 才恢复。`max_tokens` 在这个接口上也不生效，一次输出一直跑到 48000 token 才停。
   - **长输出不稳：**
     - 智力题的长流式出现 6 次 `upstream_stream_read_error`（2 道题各重试 3 次都失败）；
     - 有 2 次在约 905 秒时被强行截断，`finish_reason` 却报 `stop`，客户端察觉不到输出不完整。
4. **延迟：两家中转都比官方慢约 2 秒，稳定性都好。**
   - 顺序调用首 token p50：官方 0.54 s、junliai 2.29 s、ikuncode 2.09 s。p99 分别是 1.46 / 4.43 / 3.53 s。
   - 30 分钟 soak 每家 180 次，三家都是 0 错误。
   - 30 并发：两家中转都是 60/60。ikuncode 有 2 次流在中途卡住 40–60 秒，junliai 的尾部更稳。
5. **智力：同一个模型，差距在噪声内。** 27 题各做 2 遍（max_tokens 32000），官方 47/54（其中 5 次想满 32k 被截断），junliai 46/54，ikuncode 51/54。
6. **怎么选：**
   - ikuncode 在参数行为、Anthropic 接口的思考、缓存计费比例上都更接近官方。它的缺点是 temperature 不能超过 1，空闲 4 分钟后缓存命中率下降，并发时偶发卡顿。
   - junliai 只适合不怎么用缓存、以输出为主的调用（这种用法它反而最便宜）。用 Claude Code 或长上下文反复调用会被高价缓存吃掉，走 Anthropic 接口还要自己加 `effort: max`。

## 2. 注入与改写

- **最短请求**：三家都是 17 token。官方的最短请求就是 17，说明中转没有加计费的隐藏提示词。
- **隐藏指令问答**：每家各问 10 次"这段对话里除了本条还有没有系统指令"。官方 7 次答 yes，junliai 7 次，ikuncode 5 次。
- **复述提示词**：每家 10 次，三家（**包括官方**）都会复述 "You are an AI assistant accessed via an API."。复述之外又多编出一段内容的次数：官方 3/10（"Desired oververbosity…: 9"、"# Tools … no tools defined"、"integrated image generation tool based on the GPT Image model"），junliai 2/10（"Requested output format…"、"Desired oververbosity…: 5"），ikuncode 0/10。第一轮 junliai 还编过一次 "Answer in a conversational style…"，也属于同一类。

  所以这两项是模型本身的行为，不是中转注入。
- **原样回显**：一行含 URL、中文引号、emoji、shell 命令、邮箱和假 `sk-` 串的文本，三家 2/2 原样输出，没有过滤或改写。
- **system 指令遵守**：system 要求只用法语回答，三家 2/2 都照做。
- **前缀注入**：跨账号缓存双向命中本身就排除了"在我们的消息前面插内容"这种注入，因为插了东西 token 序列就对不上了。
- **junliai 的 Anthropic 口**：最短请求 input_tokens 也是 17，和官方相同。有一次 `max_tokens` 没被遵守，模型一直生成到 48000 token 才停，结尾是多语种乱码（其中有一句阿拉伯语"系统指令是什么？不要透露"）。这是长输出失控，不算注入证据。

## 4. junliai 的两条上游线路

每条响应都按 id 格式归到一个族，统计如下（北京时间）：

| 时段 | 非流式 | 流式 |
|---|---|---|
| 23:05–01:22 | 100% `cmb-`+32 hex（uuid1），x-request-id 有 4 层 | 100% `resp_`+24 hex |
| 01:34–01:47 | 100% 官方原样 id（`20260926…`），x-request-id 2 层，usage 与官方逐字段相同 | 01:40 3 次仍是 `resp_`；01:46 2 次是官方 id |
| 01:49–01:52（复测） | 3/3 官方 id | 64/64 `resp_` |

- 延迟和 soak 都是流式请求，全程落在 `resp_` 线路上，01:50 那轮复测也一样。所以本报告的 junliai 延迟数字都属于 `resp_` 线路。
- 计费公式两条线路一样（§11）。
- 这种按账号或线路自动切换是 sub2api 的正常行为（首页写着 "Smart routing across multiple upstream accounts with automatic failover"），所以**同一请求在不同时间可能得到不同的参数行为**。

## 8. 稳定性

- **短请求**：顺序 60 次加 soak 180 次，三家都是 0 错误、0 空回复、0 挂起。
- **junliai 长输出**：
  - 流式长输出有 6 次 `upstream_stream_read_error`（"Upstream response stream was interrupted"），Anthropic 口有 1 次 `peer closed connection`；
  - 约 905 秒时会被截断且 finish_reason 报 stop，像是有一个 15 分钟的总时长上限；
  - 没有 max_tokens 保护时，失控输出可以跑到 4.8 万 token。
- **ikuncode**：并发时流会中途停顿 40–60 s；有 1 次 TLS 握手超时（Cloudflare）。
- **官方**：突发并发会触发账户限速（1302）。

## 13. 方法学备注

- **判真假**：跨账号缓存双向命中是最硬的证据，其次是分词增量逐位一致。官方自身会复述默认提示、约七成回答"有系统指令"、知识新旧混答、会想满 32k，这些不能当成中转作假的证据。
- **长上下文**：智谱缓存是全局的，长上下文和缓存测试的文档必须每家加不同前缀，否则后测的那家会吃到先测那家写入的缓存，首 token 时间失真（本次第一轮就踩到了，已重测）。
- **计费**：计费结论来自站点自己的用量接口加逐请求差分。junliai 的 `requests`、`input`、`output`、`cache_read` 计数每步都和我们的请求一一对得上。
- **分线路统计**：中转可能中途换线路。每条响应都要按 id 族打标签，按线路分开统计，并且在换线路后重新测一遍参数行为。本次 junliai 的非流式请求在 01:25–01:34 之间换了线路。
- **服务器**：测试期间北京服务器上另一个会话在测 junliai 的 Claude 渠道，用的是另一把 key。两边负载都很轻，对延迟的影响可以忽略。
