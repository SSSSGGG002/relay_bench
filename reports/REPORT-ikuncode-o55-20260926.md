## 结论

**两条渠道是同一个上游（Kiro 通道），模型是 2026 年新一代的前沿模型，与 Opus 5.5 相符。** 智力满分，1M 长上下文可用，延迟稳定，是目前测过最好的 opus-5-5 渠道。两条渠道的实测表现几乎一样，**K2 便宜 37.5%，推荐 K2**。

- 缓存是真的，自动生效（超过约 4096 token 的前缀命中率 99% 以上），两把 key 共享同一份缓存。

## 4. 缓存（已更正：第一轮用的探针太小）

第一轮用的 5k 字符前缀，按站方计数只有约 3.3–3.9k token，低于门槛，所以没有缓存。当时得出的「≈0% 命中」结论作废。重测结果如下（Python 源码作为自然文本）：

| 场景 | K1 cc-kiro | K2 cc逆向 |
|---|---|---|
| 约 1.2 万 token 前缀，带 `cache_control` ×4 | 4/4 命中，99.7% | 首次写入，之后 3 次命中 99.7% |
| 同上，不带 `cache_control` ×2 | 命中 99.8% | 首次写入，之后命中 99.8% |
| 约 2.3 万 / 4.7 万 token，带或不带 | 首次写入，之后每次 99.9% | 同左 |
| 多轮 5 轮（首条消息放 2.2 万 token 文档） | 每轮 99.7–100% | 首轮写入，之后每轮 99.6–99.9% |

- **真缓存，自动生效**：不加 `cache_control` 也会写入和命中。计费按写入 1.25 倍、读取 0.05 倍（官方 Opus 5.5 价格），逐条对账吻合。
- **最小门槛约 4096 token**：约 3.9k 以下一律不缓存，约 4.1k 以上开始写入。官方文档里 Opus 5 是 512 token，这里的门槛可能是上游通道的策略，不作为身份证据。
- **K1 和 K2 共享同一份缓存**：K1 第一次请求就读到了 K2 刚写入的条目。这证明两条渠道是同一个上游账号池，混用两把 key 不会丢缓存。
- 命中后首字延迟没有明显下降（3–9 s）。
- 站方报的 input 对相同短请求会浮动约 ±300 token，大文档的计数则稳定。
- Claude Code 这种大前缀、多轮场景下，预计命中率在 99% 左右，非缓存率约 1%（只有每轮新增的内容）。
