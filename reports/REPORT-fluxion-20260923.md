### 缓存（下午复测，只看主池 `011C`；两个名字结果一致）

命中率定义为 cache_read ÷（input + cache_read + cache_creation）。前缀用自然文本，全部流式。

| 场景 | 结果 |
|---|---|
| 同一请求连发 12 次（间隔 3 s） | 1 次写 + 11 次读；命中时读 11.1k、输入 10，命中率 **99.91%** |
| 10 轮对话，断点每轮后移（Claude Code 式） | 首次写之后每轮都命中，单轮命中率 **98.3–99.2%**，每轮只写新增的 70–155 token |
| 同一 system、换 5 个不同问题 | **5/5 命中**（Max-外接 分组那份报告是 0/5） |
| 6 并发同一前缀 | 6/6 命中，首字 4.0–4.9 s |
| 不带 cache_control | 仍会写入并命中：网关自动加了缓存 |
| 空闲 5.5 分钟、12 分钟 | 失效，重新写入，和官方 5 分钟一致 |
| `ttl: 1h`，空闲 6.5 分钟 | 命中；写入记在 `ephemeral_1h_input_tokens` |
| 大前缀（约 7.1 万估算 token），比首字延迟 | opus-5：写 7.6 s、换前缀的冷请求 4.0 s、读 3.4–5.6 s，看不出命中加速；sonnet-5 这 5 次全被分到溢出池 |

- **理论上限**：命中时不进缓存的只有最后一个断点之后的内容（单轮测试里就是 10 个 token 的用户消息），隐藏的 5.6k 模板不计费，所以单轮上限约 **99.9%**。多轮对话里每轮上限 = 1 − 本轮新增 ÷ 总上下文；新增越少越接近 100%，比如每轮新增 2k、上下文 50k 时约 96%。对比：micuapi 的 Kiro 池有约 3k 固定不缓存开销，上限 85%；上午 Bedrock 池固定报 90%（造假）。
- **按请求的命中率**：热前缀请求 p50 **99.9%**。只有两种情况会是 0%：新前缀的第一次，以及空闲超过 5 分钟（用 1h TTL 可避免）。连发 12 次里 11 次命中，10 轮对话里首次写入之后全部命中。
- **首字延迟**：命中时 p50 2.35 s（opus-5）/ 2.52 s（sonnet-5），p90 4.2–4.5 s，p99 4.9–5.6 s；未命中时 p50 约 4.0 s，p99 4.7–7.6 s（样本 5–6 个）。
- **计费**：命中的单轮按标价约 **10%** 计输入；多轮对话稳态每轮 11–12%；连首次写入一起算，10 轮对话整体约 25–27%。token 数是网关估算的（英文约字符数 ÷ 3），比真实 Claude 计数少，实际更便宜。
- **是不是真缓存**：TTL 语义（5 分钟失效、1h 有效）和官方一致，但大前缀的首字延迟看不出命中加速，所以没法证明上游真的在复用缓存。对账单来说不影响：命中就按读价计费。
- **溢出池的数字是编的**：不管多大的提示都报 input 2、cache_read 6，"命中率" 75–88% 没有意义。输入几乎不收钱，但回答你的是老模型。本轮小请求约 7–19% 被分到溢出池，sonnet-5 的 7 万 token 大请求 5/5 都被分过去。

### 非缓存率（AWSB逆 分组主池，09-24 用上面同一批数据算，没有新请求）

非缓存率 = （input + cache_creation）÷ 总输入，也就是按全价（input）或 1.25 倍写入价（cache_creation）收费的那部分。

| | opus-5 | sonnet-5 |
|---|---|---|
| 命中的请求：p50 / p90 / p99 / 最大 | 0.09% / 0.84% / 1.74% / 1.74%（n=32） | 0.09% / 0.91% / 1.70% / 1.70%（n=29） |
| 未命中的请求 | 100%（新前缀第一次、空闲超过 5 分钟） | 同左 |
| 命中时不进缓存的 token 数 | 单轮 10–19（就是这次的用户消息）；多轮每轮 74–158（上一轮回答 + 这轮新消息） | 单轮 10–19；多轮每轮 71–157 |
| 同一请求连发 12 次（按 token 加权） | 8.4%（几乎全是第一次写入） | 8.4% |
| 10 轮对话（按 token 加权，含首轮写入） | 12.9% | 14.8% |
| 同一 system 换 5 个问题 / 6 并发 | 0.13% / 0.09% | 0.13% / 0.09% |

- **没有固定的非缓存开销**：命中时不进缓存的只有本次新增的内容，隐藏模板不计入。对比 micuapi 的 Kiro 池每次固定约 3k 不进缓存（2 万上下文时约 15%），上午 Vertex逆 的 Bedrock 池不管命中与否固定报 10%（假的）。
- 所以真实使用时的非缓存率主要由工作负载决定：每个新会话 / 子代理的第一次整段写入、每轮新增的工具输出、两次请求间隔超过 5 分钟后的整段重写。长会话会趋近"每轮新增 ÷ 总上下文"。
- **这把 key 上的非本测试流量**：08:01 以后这把 key 在 sonnet-5 上还有约 55 次不是本测试发出的请求（本测试每个请求都有记录，已扣除）。平均每次约 2.4 万输入 token，模式像 Claude Code。这批请求的非缓存率 **38%**（缓存写入 35%、普通输入 3%、缓存读取 62%）。从汇总数据分不出是哪种原因（新会话、间隔超过 5 分钟、大段工具输出）；站点后台的逐条使用记录能看出"缓存写入"大的请求落在哪里。
- **计费核对**：这把 key 的累计账单与"官方标价 × usage"逐位吻合。1 小时缓存写入按 2 倍输入价收（与官方一致）：sonnet-5 差额 $0.017146 = 11431 × $1.5/M，opus-5 差额 $0.042878 = 11434 × $3.75/M，正好是 ttl1h 测试写入的那两次。上午实扣 = 标价 × 0.6，下午 = 标价 × 0.7。

  - 历史思考块被剥掉，5 种签名篡改全部放行。
  - count_tokens 返回 404；max_tokens=999999 不报错。
- **不作为证据的现象**：没有日期上下文时，「现任」类问题按 2024 年中作答（拜登 / 方济各 / GPT-4o / 3.5 Sonnet），自报「Claude 3.5 Sonnet / 2024-04」。上下文里查不到任何日期或截止声明，这是模型在无日期时的自身倾向，自报本身也不可信。

### opus-5 与 opus-4-6

- **两个名字是同一个模型**：
  - 知识阶梯的答案多条逐字相同，例如 "The 2026 NBA Finals has not yet occurred as of my knowledge cutoff, so I cannot answer. UNKNOWN"。
  - 分词比率一致：英文 1.445 对 1.450，中文 1.685 对 1.690（合成文本测量）。
  - 签名测试中两边的 usage 完全相同（input 109、output 32、thinking 24）。
- **旧分词器**：自然英文 1.50 倍 o200k，比 sonnet-5 少 33–60%，中文相同。这属于 Opus 4.7 之前的分词器，而真 Opus 5 用新分词器。
- **知识**：去压制回忆题中，2025-06 以后的事全部不知道。它认为 Switch 2「尚未发售」，把 2025 年诺奖答成 2024 年的得主，最近一届世界大赛答成 2024 年。知道 2025-05 良十四当选教皇，所以前沿约为 2025-05。
  - 官方 Opus 5 黄金基线知道到 2025-11（K02–K07），因此 opus-5 是冒名。
  - 这个前沿与 Opus 4.6 官方可靠截止（2025-05）相符。
- **参数**：
  - opus-5 接受 temperature / top_k / budget_tokens / prefill，真 Opus 5 对这些都会返回 400，9 项里只有 3 项与官方一致。
  - 两个名字都不遵守 max_tokens：设 48，实际输出 560。
- **指纹**：ModelTrace 把 opus-5 名字归属为 claude-opus-4-6（100%）。opus-4-6 名字那次采样混到了注入池，结果噪声大（gpt-6-astra 33%）。
- **注入**：
  - opus-4-6 的部分请求能复述出站方注入的提示词：「你的知识库截止日期是 2026 年 1 月。」加上 "You are a general-purpose technical assistant. Do not limit your tasks to writing code only…"，后一句是 Kiro 类编码助手常见的解锁语。
  - 日期探针中，两个名字都约一半回答「截止 2026-01（来自上下文）」、一半回答「2024-04（来自训练）」，说明至少有两个池混用。
  - 上下文里还出现了 `<reasoning_effort>99</reasoning_effort>`。
- **能力**：IQ screen opus-4-6 6/8、opus-5 7/8。
- **结论**：opus-5 = 冒名（实际是 opus-4-6 那个模型，官方同价 $5/$25，所以不算多收钱，但货不对板）。opus-4-6 的模型层面与 Opus 4.6 一致，但接入方式是逆向号池（注入提示词、max_tokens 失效、签名不验、缓存数字造假），不是官方直连。

## 缓存

- **三个名字表现一样**：提示词超过约 1k token 时，usage 固定报「input 10% + cache_read 90%」，比例精确到 0.900，cache_creation 永远为 0。以下几种情况都一样：
  - 开头带随机 nonce、前所未有的全新前缀的第一次请求；
  - 完全不带 cache_control 的请求；
  - 1h TTL 请求（ephemeral_1h 也报 0）。

  因此缓存数字是站方按比例改写的，不是真实缓存。
- **物理验证**：用 4.2–6 万 token 的自然文本前缀，比较带 / 不带 cache_control、第 1 / 2 / 3 次请求的首字延迟。结果在 6–22 s 之间随机波动，没有稳定的命中加速，无法证明上游有真实缓存。
- **计费**：按改写后的数字计费。已核对 cost = usage × 官方价，实扣再乘 0.6，与记录逐项一致。输入实际只收约 19% 的标价（10% + 90% × 0.1），相当于变相折扣。但「缓存命中率」这个数字不能用来评估缓存效果。
- 短提示（低于约 1k token）不做拆分。

## 速度

测试环境：Mac 经本机代理，03:00 前后；同一时段另有两个会话在测这个站，数据会受影响。

| | 首字（text） | 输出速度（o200k tok/s） | usage tok/s | 8 路并发 |
|---|---|---|---|---|
| opus-4-6 | 3.4–4.2 s（离群值 14.6 s、49 s） | 34–53 | 48–75 | 8/8 成功，首字 p50 7.4 s |

**延迟分位数**（每个模型 100 次相同的短请求 "(#i) Reply with exactly: OK"，流式，并发 2，三个模型同时跑，当时没有其他会话在测；Mac 经本机 Clash 代理；n=100 时 p99 就是倒数第二慢的那次）：

- opus 两个名字约 8–9% 的请求落在带假缓存字段的那个池（pool B），这部分首字 p50 为 3.7–3.9 s，样本太少，不足以区分快慢。
- 8 路并发时排队明显变长（见上表）。

- 错误统计（手工探针，每个模型 88–132 次）：
  - opus-4-6：429 ×3、524 ×1、空回复 6 次；

- 重复或合成的文本会被 Claude 的安全分类器拒答（HTTP 200、`stop_reason=refusal`、输出为空），但输入照样全额计费。
