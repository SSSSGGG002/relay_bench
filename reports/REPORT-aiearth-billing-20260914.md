# api.aiearth.dev（AIO API）claude-opus-5 计费审计 — 2026-09-14

结论：**扣费公式没动手脚，问题出在上游回报的 token 数。** 站点把上游（Kiro/Bedrock 积分池）报上来的 cache_read / cache_creation 原样计费，而这个池报的缓存 token 数是物理上不可能的（单次请求上下文 788k、缓存读 197k 正好凑到 200k、19k 输入却写入 190k 缓存）。你那次画鹈鹕的请求 0.78 站内¥ 里，92% 是 190,933 个「缓存写入」token。

## 1. 计费公式（从日志 `other.expr_b64` 解出）

```
claude-opus-5 : tier("base", p*5 + c*25 + cr*0.5 + cc*6.25 + cc1h*10)   × group_ratio
claude-sonnet-5: tier("base", p*2 + c*10 + cr*0.2 + cc*2.5  + cc1h*4)    × group_ratio
quota = 上式(美元/百万token) × group_ratio × 500000 ；控制台显示 = quota / 500000
```

- 单价就是 Opus 5 / Sonnet 5 官方牌价（$5/$25、$2/$10，缓存写 1.25x、缓存读 0.1x）。
- 37 条日志逐条验算，公式与 quota **完全一致**（误差 0）。没有隐藏倍率，也没有按次收费。
- `官方直连-Azure-Claude-Gemini` 组 group_ratio=0.6，`普速特价` 组 0.4。**两组走的是同一个渠道 channel 952**，0.6 并没有买到不同上游。

## 7. 判断：技术问题还是恶意加价

倾向 **技术问题（上游 Kiro 适配器伪造 usage），但站方存在虚假标注和未尽核验的责任**。

指向技术问题的证据：
- 扣费公式逐条精确，没有任何隐藏倍率；站点只是把上游回报的数照单计费。
- 只有 Kiro 积分池（`msg_<32hex>` + `credit_usage`）的数字异常，`msg_011C…` 池前后一致。故意加价不会只挑一个池、只灌缓存字段。
- 同时存在明显的少收漏洞（非流式 20k 只记 9 token、OpenAI 路径 32k 记 4,243）。故意加价的站不会留这种口子。
- 灌水后的 token 数与上游 `credit_usage` 也不成比例（写 0.222 credit → 0.13，读 0.117 → 0.037，OK 0.015 → 0.0005），说明不是「按 Kiro 真实成本反算后伪装成折扣」，就是适配器算法本身是坏的。
- 同类 Kiro 适配器在别的站（wawapii）也见过 usage 畸形，是通用组件的毛病。

指向站方责任的证据：
- 「官方直连-Azure-Claude-Gemini」0.6 组与 0.4 特价组走同一渠道 952，上游是 Kiro/Bedrock 池而非官方直连，opus/sonnet 共用一个缓存。标签是假的。
- 一条请求 788k 上下文、缓存读 197,49x 卡在 200k，这种数在后台一眼可见，站方按 Opus 牌价乘 1.25 收缓存写，收了钱没核验。

结论：**不是精心设计的加价，但结果等同于加价 5–19 倍，且 0.6 组的「官方直连」宣传不实。** 拿本报告和 `/api/log/token` 导出的账单去要求按 200k 封顶重算/退差价；站方若拒改，则应视为知情获利。

## 8. 反推公式的形状（从 credit_usage 拟合）

Kiro 上游只返回 `credit_usage`（积分），不返回 Anthropic 式 token 数；适配器必须编一组 token 填进 usage。用本次 Claude-Code 风格探针（F2、R0–R3）拟合：

| 字段 | 与 credit 的比值 | 稳定性 |
|---|---|---|
| cache_read_input_tokens（重发）| **≈ credit × 1,000,000** | 998k–1,035k，±2% |
| cache_creation.ephemeral_5m（首发）| ≈ credit × 210,000 | 210k–212k |
| cache_creation_input_tokens（首发，站点按此计费）| ≈ credit × 88,000 | 87.8k–91k |
| input_tokens | 与 credit 无关，接近真实 | 6.7k–7.1k |

即：重发一次的 token 数 = 积分数 ÷ Anthropic 缓存读单价（$0.5/M），相当于适配器假定 1 credit = $0.5 再按牌价反除。tiny 请求（B）和多轮消息（F5）、sonnet 首发不符合同一比例，说明还有别的分支，但 Claude Code 主流请求走的就是这条线。

为什么会算错真实费用：Kiro 按次收积分（一次请求约 0.1–0.2 credit，缓存命中只便宜一半），Anthropic 按 token 收钱且缓存读只有输入价的 1/10。适配器把「这次花了 0.117 credit」硬翻译成「读了 117k 缓存 token」，站点再按 $0.5/M × 0.4 收 0.037，四个环节里没有一个数是真实 token。上下文超过 200k、卡在 199,99x（封顶）都是这条公式的副产品。
