## 5. 缓存

- 约 5k token 的 system 前缀，带 `cache_control` 连发 8 次、不带 `cache_control` 连发 4 次、放在首条用户消息里多轮 6 轮、闲置 6 分钟后再发 2 次：**20 次请求 0 次命中**。每次都报 `cache_creation` 约 5.1–5.5k，`cache_read` 只有 14–127 这种小数字。
- 小请求固定报 `input 11 + cache_read 81`：这 81 是编出来的数字，不是真命中。
- 计费：usage × Opus 5.5 官方价（$4 / 写入 $5 / 读 $0.2 / 输出 $20）× 0.4，与后台逐项吻合。问题在于前缀每次都按**写入价**（输入价 1.25 倍）计费，而真缓存命中应该按读取价（0.05 倍）计。**同一个前缀重复发送，比真缓存贵约 25 倍**。在 Claude Code 这种大前缀、多轮的场景里，这是最大的成本坑。
- 理论缓存命中率：0%。非缓存率（input + 写入 ÷ 总输入）：≈ 98–100%。
